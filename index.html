01

Repository (repo)

The project folder, tracked by Git and hosted on GitHub et al.

A repository is that folder once Git is watching it. Every snapshot, branch, and author lives in a hidden .git directory inside the project. A host such as GitHub, GitLab, or a company server stores another copy of the same history. That hosted copy is a remote. The folder on your machine and the remote are two homes for one history, not a folder and a backup of only the latest files.

Command git init

Considerations

  • Keep a single .git at the project root. A repository nested inside another one is a frequent accident, usually from cloning into a folder that is already tracked.
  • Issues, reviews, and permissions belong to the host. They are not stored in .git. Git itself is the history; GitHub is one place to put it.
  • Anything you commit can be recovered later. That includes tokens, passwords, and huge binaries, which are painful to purge after they have been pushed.
  • Add a .gitignore before the first commit so dependencies, build output, and local environment files never become part of the history.

02

Clone

Download a copy of the code to your machine.

Clone copies a repository that already lives on a host. You get the files, the commits that produced them, and a remote named origin that remembers the URL. That is the usual first step on a project someone else created. You clone once per machine. After that, pull and push keep the two copies in step.

Command git clone <url>

Considerations

  • A clone is the full history, so you can read old commits, branch, and bisect while offline. It is larger than a zip of the latest files, and that is the point.
  • The folder name defaults to the repository name. Renaming the folder does not break Git. The remote URL is what matters.
  • HTTPS and SSH change how you authenticate, not what gets downloaded. Use the one your host already has keys or a login for.
  • A shallow clone (git clone --depth 1) saves time on a huge repository. Some history-dependent commands need the rest of the commits, so use it when you only need the latest snapshot.

03

Branch

A safe parallel timeline to the main codebase.

A branch is a movable name for a commit. main is simply the branch everyone treats as the stable line. When you make a feature branch, you get a second pointer. New commits advance that pointer and leave main where it was. Switching branches changes which snapshot your files match. It does not make a second copy of the project.

Command git switch -c feature/nav-contrast

Considerations

  • Older guides say git checkout -b. git switch -c does the same job and is harder to confuse with restoring a file.
  • Name the branch after the change (feature/nav-contrast), not after yourself. The name is what reviewers see on the pull request.
  • Uncommitted edits come with you when you switch, unless they collide with the other branch. Commit or stash first when Git refuses the switch.
  • Short branches are easier to merge. A branch that lives for weeks has to keep absorbing new work from main.
  • Deleting a merged branch deletes the label, not the commits. Those commits are now reachable from main.

04

Commit

A snapshot + message describing your changes.

A commit stores the state of the tracked files at one moment, plus who made it, when, a message, and the id of the parent snapshot. You build that snapshot by staging files. Git can show you later what changed between any two commits, and it can put your files back the way they were. Making the commit does not publish it. The remote hears about it when you push.

Command git add styles.css git commit -m "Raise nav contrast"

Considerations

  • Stage on purpose. git status before you commit will catch the env file or the screenshot you did not mean to include.
  • Write the message in the imperative, and say why when the diff will not: “Raise nav contrast in dark mode.”
  • A commit should be a state you could return to. Local “wip” commits are fine, and worth squashing before anyone else has to read them.
  • Amend only a commit you have not pushed. Rewriting a shared commit forces everyone else to reconcile their copy.

05

Push / Pull

Upload to / download from the hosted repository.

Push sends commits you have, and the remote lacks, up to the hosted repository. Pull brings commits the remote has, and you lack, down into the branch you have checked out. Pull is a download plus an integration: fetch, then merge (or rebase, if you have set that). Files you have edited but not committed stay put. They are not part of either transfer.

Commands git push git pull

Considerations

  • The first push of a new branch needs an upstream: git push -u origin feature/nav-contrast. Later, plain git push and git pull know the match.
  • If the remote rejects the push, it has commits you do not. Pull, resolve if you need to, then push again.
  • git fetch downloads those commits without merging them, which is useful when you want to look before you integrate.
  • Forcing a push replaces commits on the remote. That throws away other people’s work on that branch. Reach for it only when you mean to rewrite history you alone are using.

06

Diff

The visual difference between two versions of code from two different branches.

A diff lists what would have to change to turn one version into the other. Removed lines and added lines are marked, with a few unchanged lines around them so you can see where you are. You can diff your uncommitted edits, the files you have staged, two commits, or two branches. The review on a pull request is that comparison, plus the comments people leave on it.

Command git diff main...feature/nav-contrast

Considerations

  • git diff is what you have not staged. git diff --staged is what the next commit will contain. Glance at both before you commit.
  • Three dots, main...feature, means “what the feature branch changed since it split from main.” Two dots compares the two tips, which also includes new work that landed only on main.
  • Lockfiles, generated CSS, and whitespace-only edits bury the change a reviewer should see. Look at those separately when they are not the point.
  • A diff shows what changed. The commit message and the pull request description have to carry why.

07

Merge

Combine a branch back into another branch.

Merging takes commits that are on another branch and joins them into the branch you have checked out. If that branch has not moved since the split, Git can fast-forward: it slides the pointer forward and does not write a new commit. If both sides have new commits, Git writes a merge commit with two parents, one for each tip. The side timeline stays visible in the history.

Command git switch main git merge feature/nav-contrast

Considerations

  • You merge into the branch you have checked out. Switch to main first when main is the branch that should gain the work.
  • Merging main into your feature branch along the way keeps the final merge small. A week of divergence becomes a pile of conflicts.
  • A fast-forward leaves a straight line, which is tidy and hides the fact that a branch existed. A merge commit keeps that record. Teams pick one on purpose.
  • If the same lines changed on both sides, the merge stops for a conflict. Resolving it is part of finishing the merge, not a separate kind of Git object.

08

Rebase

Replay your commits on top of the latest main.

Rebase takes the commits that exist only on your branch and reapplies them, one at a time, as if you had started from a newer base. Usually that base is the latest main. The changes match the old commits. The commits themselves are new, with new ids, and the history reads as a straight line. The drawing is the difference between “we diverged” and “this work sits on top of current main.”

Command git switch feature/nav-contrast git rebase main

Considerations

  • Rebase rewrites commits. Use it on a branch you have not shared, or that you alone are pushing. Rewriting a branch other people have based work on makes their copies diverge.
  • After a rebase of something already pushed, updating the remote means a force push. --force-with-lease refuses to overwrite commits you have not seen. A plain force push does not.
  • git pull --rebase replays your local commits on top of what you just downloaded, instead of adding a merge commit.
  • If a replay hits a conflict, fix that one commit and continue. Git then replays the rest. Abort returns the branch to the moment before the rebase.

09

Merge conflict

Two changes touched the same lines; you choose.

Git will combine edits that land on different lines. It will not guess when both sides changed the same lines, or when one side edited a file the other deleted. It stops and marks the file. You edit it down to the text that should remain, remove the markers, and stage the file. That human choice is the resolution. The merge or rebase finishes only after every marked file is staged.

Then git add styles.css

Considerations

  • The markers <<<<<<<, =======, and >>>>>>> are ordinary text until you delete them. Leaving one in the file ships it to the product.
  • During a merge, “ours” is the branch you are on and “theirs” is the branch you are bringing in. During a rebase those names flip, because your commits are the ones being replayed.
  • Overlapping edits are not a verdict on who was right. When the two versions encode different intentions, ask the other author before you pick a side.
  • Read the whole file after you resolve it. A conflict on font-size can sit next to a color change that was fine and should survive.

10

Pull Request (PR)

“Please review and merge my branch.”

A pull request is a conversation on the host, attached to a branch, asking other people to review the diff and merge it. GitLab calls the same object a merge request. The request holds a description, line comments, checks, and a merge button. Pushing more commits to that branch updates the same request. Opening it changes nothing in main until someone merges it.

On the host gh pr create

Considerations

  • The diff already shows what changed. Use the description for the problem, the approach, and what you checked in the browser.
  • A pull request that fits in one review gets a better review. Split unrelated edits into separate branches.
  • Reviewers can comment, request changes, or approve. Answer with new commits on the same branch rather than opening a second request.
  • Branch protection can require an approval and passing checks before the button works. That rule lives on the host, not inside Git.
  • Mark it draft while it is not ready. People treat an open request as a request for their time.

11

Issue

A ticket: bug, feature, or task.

An issue tracks a unit of work on the host. It has a title, a description, labels, assignees, and a thread. It is not a Git object and it does not change any file. The code change still happens on a branch and lands through a pull request. The issue is how the team agrees what that change is for, and how they know when it is done.

On the host gh issue create

Considerations

  • One issue, one outcome. A ticket that asks for three unrelated changes is hard to review and hard to close.
  • A useful bug report says what you did, what you expected, and what happened. A useful feature says who it is for and what done looks like.
  • Labels such as bug and design keep a long backlog readable. They are not a substitute for the description.
  • Writing Fixes #18 in the pull request links the two. On GitHub, merging that request can close the issue.
